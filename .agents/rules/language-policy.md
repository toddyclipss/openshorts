# Mandatory English Language Policy

## 1. Overview & Policy Statement

OpenShorts is an international, open-source project with global contributors and production users. To maintain architectural clarity, maintainability, and seamless collaboration across international developer teams and automated AI agents, **the English language is mandatory across all aspects of this repository**.

Non-English languages (specifically Portuguese, Spanish, or other languages) are strictly prohibited in project assets, code, and version control metadata.

---

## 2. Scope & Enforcement Rules

This policy applies unconditionally across the entire lifecycle of the repository:

### 2.1 Source Code Identifiers
- **Identifiers:** All variables, parameters, functions, methods, classes, modules, constants, enums, type definitions, and file names must be clear, idiomatic English.
- **Prohibited:** Never use non-English terms in identifiers (e.g., avoid `corte`, `arquivo`, `legenda`, `processar_video`, `saida`, `tela`).
- **Idiomatic Naming:** Follow standard English domain nomenclature (`cut_clip`, `subtitle_stream`, `output_path`, `frame_sampler`, `crop_box`).

### 2.2 Comments, Docstrings & Annotations
- **Comments:** All single-line comments (`# ...` or `// ...`), block comments, and inline clarifications must be in English.
- **Task Markers:** All `# TODO`, `# FIXME`, `# NOTE`, `# HACK`, and `# BUG` annotations must be written in clear English.
- **Docstrings:** All module, class, and function docstrings (`"""..."""` or `/** ... */`) must describe behavior, inputs, return values, exceptions, and side effects in English.

### 2.3 Documentation & Specifications
- **Project Documentation:** All Markdown files (`README.md`, `CLAUDE.md`, `GEMINI.md`, `design.md`), technical docs under `docs/`, architecture diagrams, runbooks, and inline diagrams must be in English.
- **API Documentation:** OpenAPI schemas, FastAPI route summaries, parameter descriptions, model field docstrings, and response examples must be entirely in English.

### 2.4 User Interface & System Feedback
- **Frontend Chrome:** All dashboard labels, button copy, modal texts, error banners, tooltips, step indicators, and form inputs must be English.
- **Exceptions & Logs:** All backend log messages, audit events, telemetry payloads, console prints, and HTTP error responses (`HTTPException(detail=...)`) must be in English.
- *Permitted Exception:* End-user content processed by the tool (e.g., source video audio in Spanish, German subtitles generated by ElevenLabs/Whisper, or user-typed captions) preserves the user's chosen target language.

### 2.5 Version Control Metadata
- **Commit Messages:** All git commit titles and extended descriptions must be in English. Adhere to conventional commit standards (e.g., `feat(reframe): optimize face tracking bounding box`, `fix(subtitles): resolve ASS timestamp offset`).
- **Branch Names & PRs:** All git branches, PR titles, PR templates, and issue discussions must be formulated in English.

---

## 3. Auditing & Refactoring Guidelines

When inspecting existing code or introducing changes:
1. **Audit Check:** When editing any module, scan for legacy Portuguese or other non-English words in strings, logs, comments, or variable names.
2. **Safe Translation:** When translating existing code identifiers or comments into English, ensure no runtime regressions or broken external API contracts occur. Keep serialization schemas backward compatible.
3. **Automated Search:** Use case-insensitive grep/regex searches (e.g., searching for common Portuguese roots like `legenda`, `corte`, `processamento`, `erro`, `usuario`) to eliminate legacy language remnants.
